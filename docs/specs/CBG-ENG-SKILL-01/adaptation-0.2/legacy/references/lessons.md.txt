# Apply lessons from the knowledge wiki and docs

Use task-relevant prior learning to change a concrete plan, precaution or check. Do not copy the knowledge base, add a second lesson registry or make historical advice authoritative.

## Retrieve before planning and delegation

- Use the configured wiki MCP registration, never an assumed bundle or CLI. Start with bundle discovery and concept search as live rules require; recall active memory with the goal plus actual subsystem, symbol, error or decision terms. A broad “lessons” query alone is not adequate retrieval.
- Search relevant repository docs through the correctly bound graph, then read the selected canonical docs/specs/review/runbook/evidence sections. Wiki-only lookup does not satisfy the docs requirement. Follow useful citations/backlinks/neighborhoods when needed, not indiscriminately.
- Read the selected actual sources, not only search snippets or a coordinator paraphrase. Keep searches bounded to decisions/failure modes that matter; an honestly empty relevant search requires no filler.

## Check standing and applicability

For each material lesson, establish its source identity/locator, lifecycle/approval standing, cited revision/environment/path and caveats. Distinguish approved contract, verified procedure, historical incident, proposal and unresolved observation.

General wiki search/links can expose candidate, quarantined or superseded memory; a hit is not active/approved practice. Active recall is still advisory and can be irrelevant to this revision. A retrieval timestamp is not a verification timestamp; no invented expiry/TTL or assumption of permanent freshness.

Verify mutable facts with current graph/source/executed evidence. For runtime claims, compare the actual running version/path/environment, not merely merged source or wiki text. Use the relevant current checkout's bindings; another checkout's graph or source is not proof about this one. Historical fixes do not prove a present defect or present implementation.

Resolve conflicts against applicable instructions, Scryer intent and approved specs/contracts, using current source/tests as implementation evidence. Do not choose by whichever source is newest/convenient. Preserve counterevidence and failed expectations. If recalled memory is established unsafe/contradicted, follow live quarantine/supersession rules within authorized scope; read-only reviewers report rather than mutate it. Never automatically activate/re-ingest a search result.

## Carry lessons into execution

In the **canonical Scryer execution brief**, add only:

- source links/locators and relevant revision/caveat;
- why the lesson applies to this slice, or what remains unverified;
- its concrete implementation precaution and relevant check/review question.

This is an application of knowledge, not a copied page or a second durable brief. Keep evidence with the canonical spec/reports and delivery status in Linear. Do not create architectural claims just to host a lesson.

Require each coding agent to read its selected source sections before dependent edits. In its return, it identifies how implementation/tests address the applicable implications, or gives a reasoned non-applicability/conflict. A “read wiki” checkbox or summary-only handoff is not enough. Avoid redundant/unrelated tests and changes merely because a lesson exists.

At acceptance/review, inspect actual changed code and executed check evidence against those implications. A proposed test, attached test, passing unrelated suite or historical result is not a current pass. Preserve exact tested revision, native environment/caller/mode and exclusions where relevant.

## Refresh, outages and learning

Refresh narrow retrieval when entering a new subsystem, scope materially changes, a familiar failure occurs or resume reveals relevant changed evidence. Do not repeatedly dump every doc into every worker.

A source/tool failure is not an empty result. Report unavailable required retrieval and pause its dependent work/conclusions; continue independent already-approved work only. No silent cached-summary, different-project or unauthorized CLI fallback. An uncertain remote write needs state reconciliation, not blind retry.

At handoff cite the lessons that materially affected the outcome, checks/results and unresolved gaps. Explicitly assess genuinely new reusable knowledge; use live wiki/memory provenance, candidate verification/lifecycle and wiki validation/link/build gates when warranted. No raw sessions, copied outputs, secrets, transient status or filler records. Existing source references are not themselves a reason to create more memory.
