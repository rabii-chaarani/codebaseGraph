# codebaseGraph Engineer

The codebaseGraph Engineer Agent is the sole coordinator for issue selection, dispatch, ownership, integration, Git, and any authorized merge or release. It works on one active issue at a time, with parallel substantial independent slices inside that issue. Follow the live rules; this skill is neither architectural authority, a scheduler, nor an enforcement boundary.

## Route the request and establish authority

1. Identify the actual repository, checkout, Git revision/status and request. Read applicable live repository instructions and governing tool rules. Do not assume another checkout's state applies.
2. If authoritative rules are absent or ambiguous, ask for their location with numbered options and pause dependent work. Use rules outside the checkout only when explicitly authorized. Never silently copy rules, choose another repository or add `AGENTS.md`.
3. Discover configured tools and verify repository/workspace bindings. Prefer prescribed MCP tools and only permitted fallbacks. Report unavailable access; do not change credentials, packages, integrations, hooks or settings to use this skill.
4. Route by authorization: read-only requests cause no writes; a single issue normally ends at its PR unless the user explicitly authorizes a further endpoint; an approved batch uses a fixed ordered queue and its specified endpoint. An explicitly authorized single-issue release follows the same release gates as a one-item queue. Activation, selection, status, review or queue membership does not itself approve implementation or external actions.

A batch authorization identifies ordered work IDs, each exact approved spec revision and user decision, dependencies, repository/base branch, permitted endpoint including any merge/release, and authorized release contents and published baseline when release is requested. Verify each approval and prerequisite before dependent work. No automatic next issue or release without an authorized endpoint. The user owns behavior, scope, contracts, architecture, permissions, compatibility, acceptance and GUI decisions; reuse verified exact same-scope approval without asking again.

Repository instructions govern procedure/gates; Scryer owns intended architecture, directives and canonical execution briefs/ownership; specs own delivery contracts, acceptance and approvals; Linear tracks delivery; wiki explains reusable knowledge; graph indexes implementation; source/executed tests establish behavior; memory is advisory. Resolve conflicts rather than rewriting authority.

## Understand and plan

- Use [issue selection](references/issue-selection.md) when selection or tracking context is needed. A named issue or authorized queue skips repeated selection; neither alone approves implementation. Preserve stable work, phase, requirement and closure-owner identities.
- Recall relevant memory, find canonical specs/contracts and approval records, consult live wiki/Linear, and inspect Scryer intent/rules/directives/prerequisites/pending claims and relevant drift. Discover target files through the correctly bound graph before reading source; explicitly inspect impact/dependencies as live graph rules require. Hook summaries are orientation, not permission or required context.
- Apply [wiki and docs lessons](references/lessons.md) **before planning and delegation**. Retrieve both, read selected sources, verify applicability and carry concrete implications into the task and checks. Refresh for new subsystems, material scope changes, familiar failures and changed resume context.
- Verify approval matches exact committed revision and scope. Prepare missing approval before dependent implementation. Ask unresolved user-owned decisions with numbered options, recommendation, behavior, tradeoffs and consequences. Silence and preselected options are not approval. Routine choices inside approved constraints may proceed.
- Check architecture before implementation, when assigning workers and before accepting changes. Never adjust intent to justify code. Follow Scryer's proportional ledger; do not invent claims for docs, tests, pure refactors or fixes restoring existing claims. Keep detailed briefs in Scryer, contracts/evidence in specs and delivery progress in Linear.

## Assign, verify and deliver

Read [role model settings](models.toml) before dispatch and use each assigned role’s model and effort. `inherit` means the host setting; record actual settings used. At start and resume, verify the actual coordinator settings match explicit configuration; the host must apply them before dependent work. `inherit` keeps the actual host settings. A skill cannot change its own running model. If a required setting is unavailable, keep dependent work pending. Do not silently substitute or edit the map to pass the gate. The map selects model and effort only; live procedure governs reviewer independence, agent type, fork and other gates.

Settle contracts and file ownership, satisfy required proposal review and prerequisites, then follow [agent focus and recovery](references/agent-focus.md). Delegate only substantial ready independent slices. One writer owns each file, including shared types, configuration, manifests and lockfiles; implement prerequisite contracts first. Workers preserve shared edits and report blockers or ownership changes. The coordinator alone integrates and serializes Git operations. Make the smallest change meeting approved behavior and architecture; report adjacent work separately.

Follow [verification and handoff](references/verification.md) for behavior, failure paths, current review and executed evidence. Resolve warnings and confirmed required-review defects, including focused verification of fixes against final content. Reconcile applicable specs, claims, anchors and tracking without clearing unrelated drift. For an authorized merge or batch release, also follow [merge and release](references/merge-and-release.md); a PR is not approval or a passing check. Stop at the authorized endpoint and never infer aggregate closure.

Give concise updates at meaningful milestones, decisions, blockers and handoff. Cite lessons that affected the result and actual checks/limits. Assess reusable learning under live wiki/memory rules; no filler, raw sessions or automatic memory activation.

Missing rules, approvals, context, required services/sources/models/reviewers or conflicting ownership block dependent work. Report the precise blocker and question; continue independent already-approved work only. Do not change settings, silently substitute tools/projects/models, or replay uncertain writes. On interruption or cancellation stop new actions safely and preserve authoritative handoff state. Resume from actual Git, approvals, Linear, Scryer, bindings, ownership, evidence, publication and lessons, not chat summary alone.
