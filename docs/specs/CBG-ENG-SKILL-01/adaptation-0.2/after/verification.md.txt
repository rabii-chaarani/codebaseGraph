# Verification, delivery and skill checks

## Verify the selected issue

Trace acceptance to approved requirements/contracts, applicable architecture claims and actual changed anchors. Run relevant behavior and failure checks in the target project's own environment and required native platforms; the orchestration REPL is not that project's runtime. Follow live Scryer test-radius/report/attachment/fold/drift rules only where applicable. Attached tests or configured CI are not passing execution; no invented claims/JUnit or clearing unrelated drift.

Check that applicable wiki/docs implications affected the implementation or a justified relevant check. Record exact source/tested/reviewed revisions, commands/methods, environments, results, report links and limitations. Reconcile stale/ambiguous results rather than count them as current evidence. Resolve warnings and every confirmed required-review defect; rerun affected checks and get focused reviewer verification against final content.

Use required fresh independent proposal/final reviewers, their live review skills and the [role model settings](../models.toml). If that exact execution is unavailable, keep the gate pending and ask the user; do not silently substitute. Report actual settings and snapshot, not a capability the runtime does not expose. A review recommendation does not replace user approval or executed tests.

## Deliver without claiming extra authority

After applicable acceptance/review gates pass, coordinator commits relevant changes with a Conventional Commit, pushes, creates the PR and reconciles authorized tracking/spec/Scryer evidence under live rules. Preserve immutable approval references and distinct gate owners. If a remote/tracking operation is unavailable or uncertain, report pending synchronization/known identities and reconcile before retry; no duplicate or false success.

A concise handoff identifies outcome, spec/approved revision, issue/PR/commits, actual checks/reviewer settings/final snapshot, applied lessons, remaining gates/limits and reusable-knowledge assessment. Distinguish the PR endpoint, an issue merged with successful main CI, a released batch and owner-controlled aggregate closure. Follow [merge and release](merge-and-release.md) only when the endpoint authorizes it. Stop at the authorized endpoint; aggregate closure remains with its owner.

## Validate changes to this skill

Run the skill-creator structural validator and check internal reference links, byte hashes and discovery-precedence collisions. Check valid frontmatter, matching allowed name/directory, a nonempty trigger-specific description within its limit and enabled automatic model invocation. Re-read actual files; text checks are not behavior evidence.

Verify native discovery/loading in a fresh or reloaded session in the intended checkout through the host interface. Record the interface, action, discovery, invocation and routing observations. An explicit file read does not prove native loading. Model-directed routing is not a guaranteed hook. If only YAML parsing/path existence is available, leave loading pending; do not equate a manually pasted prompt with a loaded skill.

Use blind isolated fictitious fixtures, no live services, issues/writes or real coding workers, for scenario walkthroughs. Keep expected answers separate from participant inputs; capture actual responses/actions and independently evaluate them. Cover:

- missing rules/scope, read-only requests, named issue versus recommendation, ranked ready/blocked choices and no-ready preparation;
- missing/mismatched approval, architecture conflicts/prerequisites and one selected issue/one writer;
- both wiki/docs retrieval, source lifecycle/revision/applicability, Scryer implications, worker source reads and implementation/check reflection;
- new subsystem/familiar-failure refresh, empty search versus outage, permitted fallbacks and uncertain writes;
- unrelated edits/overengineering, stopped-writer-before-replacement, preserved dirty-worktree resume;
- evidence honesty, review failures/pending gates, concise handoff and authorization-based next-issue, merge and release boundaries;
- blocked queue items and independent bypass, strict server-enforced base freshness, release delta/authorization, exact artifact promotion and uncertain publication recovery.

Map results to the approved acceptance criteria and actual artifact hashes/settings. Walkthroughs establish bounded instruction-following observations, not production integration, hard enforcement or platform qualification. No real-issue trial without separate authorization. Do not claim product tests ran for Markdown-only changes or create filler wiki/memory records from synthetic results.
