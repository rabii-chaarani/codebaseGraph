Ladybug evaluation is complete but does not authorize adoption. Official 0.22.0 still has the guard; a twice-reproduced failed-checkpoint/successful-retry/reopen sequence preserved rows but lost PK lookup visibility ([upstream #1406](https://github.com/LadybugDB/ladybug/issues/1406)). Bulk COPY row payload is not WAL-backed; a commit record does not guarantee durability after checkpoint failure ([PR1204](https://github.com/LadybugDB/ladybug/pull/1204), [PR1361](https://github.com/LadybugDB/ladybug/pull/1361)). Treat a failed mutating operation as an uncertain candidate, not proof of rollback or durable success. This is not a proven diagnosis of the original incident.

**Outcome sought:** either one successful, correctly reopened candidate is published, or the first failure reaches the caller and the existing graph remains readable and unchanged. Bounded sequential files reduce per-COPY input size; they do not guarantee every workload fits Ladybug's native memory.

## 3. Recommended scope and decision

### Scope A — recommended first delivery

1. Run each mutating phase at most once per candidate. On any native `Err` from schema/COPY/hash/post-COPY/explicit-checkpoint execution, stop the load and propagate that failure. Remove the blanket `already exists` / `exists already` / `already installed` error-to-success mapping in both writer paths. Successful idempotent SQL/results remain successful; an actual native error is not a verified no-op merely because its text matches. No index repair, duplicate skipping, implicit same-candidate retry, or success inferred from row counts.
2. Use `LadybugWriteRequest.buffer_pool_bytes` for that single execution. This is already computed from configured resources (128–384 MiB for normal materialization), not a new limit. Remove the isolated 256 MiB start / 64 MiB escalation mechanism and fallback write-operation retry. Read-only transient retries stay unchanged.
3. Bound final JSON and connector files using the existing `spill_chunk_mib` byte value already used for spill/record limits. Keep one sequential COPY per file and preserve the current early-hash-index-after-first-success ordering for repeated node tables.
4. Bound both native diagnostic ingestion and returned phase-failure context using the existing 64 KiB child-error budget. Read only a file tail/window before allocation; never read all stderr then truncate it. Cover both inherited and standalone/guarded execution routes on the selected main baseline; skip unused successful-exit stderr rather than ingesting it unboundedly. Reserve space within the returned phase diagnostic for bounded parent-known phase/kind, COPY ordinal/total and target, effective pool and worker ceiling; retain a bounded native tail from the first failed attempt and identify truncation. The bound is on the assembled isolated-phase diagnostic, not every later API/JSON envelope. Distinguish COPY-query from explicit-checkpoint failure without claiming the engine-internal outcome is known. Cleanup errors are secondary.
5. Regress actual isolated/reopen behavior, lookup/endpoint correctness, prior-active preservation and bounded resource failure. Do not broaden production validation into an expensive full-graph audit.

**Behavior changes requiring sign-off:** there is no immediate automatic recovery from a failed database mutation; the operation fails safely instead. Raw schema/extension/post-COPY errors previously hidden by substring matching now fail the invocation; intended idempotent setup must return success and pass its regression. The initial native pool may rise from 256 to the already configured 320/384 MiB ceiling. This changes startup RSS and must pass the existing worker RSS supervisor. More final files mean more sequential child phases/checkpoints. No new public setting or resource ceiling is proposed.

### Scope B — optional later delivery, NOT included in Scope A approval

Restore automatic pool escalation only by reconstructing an entirely fresh disposable candidate from the same completed immutable staging. This is a new sequencing/recovery behavior, not something current publication recovery already promises.

Required order: failed attempt stops → existing lifecycle owner proves all owned writers exited → storage owner abandons its complete candidate and sidecars under ownership → owner allocates a fresh candidate → replay the complete schema/node/index/connector/post-COPY plan, not only the failed statement → reopen and validate → publish once. If teardown/cleanup/ownership is uncertain, stop, preserve evidence and keep the active graph. Never reset an arbitrary `db_path` from inside `run_phase`.

Before Scope B can be approved, specify the finite attempt/pool schedule within the existing ceiling, immutable-staging lifetime, sidecar/manifest rebinding, writer-lock lifetime, durable crash/cleanup behavior, and bounded diagnostics across attempts. `StorageExecution` is the existing owner boundary ([materialization.rs:384–503](../../../src/api/materialization.rs#L384)); it currently has no retry loop ([311–319](../../../src/api/materialization.rs#L311)). Scope B must not reparse changed live source while claiming to replay the same staged generation. Runtime hooks/journals and tests must follow the approved main lifecycle contract, not the weaker old checkout. Detailed design belongs to a separate Scryer brief and spec amendment; no Scope B implementation is authorized by this draft.

### Alternatives and tradeoffs

| Option | Advantage | Cost / reason not selected |
| --- | --- | --- |
| A: fail closed + bounded sequential files + one configured pool | Small, explicit correctness boundary; no new reset/retry state machine; avoids false rollback assumptions. | Some builds fail instead of recovering automatically; higher initial pool; more phase overhead. Recommended. |
| A+B: automatic whole-candidate reconstruction now | Can recover from a low-pool attempt without unsafe replay. | Needs new owner-level sequencing, crash/staging/sidecar rules and extra fault tests. Defer unless user selects it. |
| Fail closed but retain the 256 MiB starting pool | Least initial memory change. | Rejects loads that currently succeed after reaching their already configured larger pool. Viable safety-only alternative if startup RSS is the priority. |
| Eager/create-after-error hash indexes, duplicate skipping or disabling auto-checkpoint | May hide this guard or reduce checkpoints. | Does not prove an uncertain mutation rolled back or became durable. Rejected as a correctness fix. |
| Upgrade to 0.22.0 alone | New upstream features and API-compatible build observed. | Guard and checkpoint/PK-integrity blocker remain; ABI/storage/platform work is independent. Excluded. |

## 7. Risks, mitigations and stop conditions

| Risk | Mitigation / stop condition |
| --- | --- |
| Fail-closed removes successful low-pool recovery; starting at the configured maximum raises initial RSS. | User explicitly approves the change. Measure with existing RSS tests/reference workload inside unchanged ceilings. If that profile fails, stop and select the 256-start fail-closed alternative or separately design Scope B; do not silently raise limits. |
| More chunk files trigger more index/child/checkpoint overhead and can still exceed native memory. | Reuse early indexing; verify isolated boundaries and representative existing workload without inventing an SLA. Do not claim a file bound caps database/index memory. Surface native failure rather than replay. |
| Smaller files increase the retained/cloned COPY-statement list with chunk count. | The existing sink keeps a `Vec<String>` and the writer clones it ([accumulator.rs:695](../../../src/staging_writer/accumulator.rs#L695), [writer.rs:30](../../../src/staging_writer/writer.rs#L30)). Qualify Rust/control memory with the unchanged resource suite. A file-size bound is not a cardinality-independent bound on the entire staging/control state. Do not introduce a streaming plan subsystem unless measured evidence makes it necessary and the user approves that scope. |
| A regression passes with correct counts while PK entries/endpoints are wrong. | Reopen in a new process and compare expected fixture IDs through both scan and PK lookup plus connectors. No count-only correctness claim. |
| The source checkout lacks newer teardown/guardian safety described by contracts. | Implement on an approved main baseline with existing lifecycle fixes; reverify actual source. Do not backport process safety by assumption or delete a possibly live candidate. |
| Fault test never reached the target mutation, or uses only in-process unit fallback. | Require fixture readiness/mutation evidence and observed isolated helper invocation. Record pre-fault setup failures separately. Keep engine full-disk experiment evidence separate from deterministic application policy tests. |
| Existing unrelated dirty specs/wiki work is overwritten or unrelated model drift folded. | Use a separate worktree; touch only approved files; preserve existing identities/approvals; scope reconciliation. No global drift reset. |

Pre-mortem: (1) a COPY commits but acknowledgement fails: no replay/publication and the old graph survives; (2) two valid chunks expose missing PK entries after reopen: the PK/connector oracle fails the build's qualification; (3) process death leaves an uncertain writer: existing main containment proof blocks cleanup/new mutation until safely resolved. These are planned tests, not new runtime guarantees proven by this document.
