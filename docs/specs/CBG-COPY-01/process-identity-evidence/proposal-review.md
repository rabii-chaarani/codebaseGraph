## Evidence and challenge results

1. **The existing oracle confuses a PID with a process incarnation.** `tests/copy_phase_process.rs:417–424` counts unique numeric PIDs across COPY records. The retained `failed-artifact/platform-test.log` establishes 55 unique PIDs versus 56 records in the named Windows test at that assertion. It does **not** establish whether PID reuse or genuine process reuse caused that specific run: `phases.jsonl` is unavailable. Keep that cause unproven in the handoff.
2. **The replacement tests the intended property without accepting same-process reuse.** A 256-bit random token initialized through one process-global `OnceLock<Result<String,String>>`, generated in the executing helper rather than the request/parent, stays constant across multiple requests/records in that native process. A set of those tokens therefore rejects a helper executing multiple COPY phases, while accepting separate helper instances whose numeric PIDs happen to match. A token per event/request would defeat the test and is explicitly excluded. Normal helper execution uses a fresh executable, not a fork-only child inheriting an initialized singleton.
3. **The mechanism is feasible and proportional.** `src/db_writer/phase.rs:354–369` performs the real mutation before its debug-only trace hook; `:402–465` already owns that internal trace and acknowledgement-failure injection. `Cargo.toml:43` already declares `getrandom = "0.3.4"`; no dependency, product protocol, request, loading, containment, public API, or resource change is needed. Keep token generation/encoding inside the existing debug instrumentation, after checking that tracing was requested. Entropy failure should propagate as a test-instrumentation error; no PID/time/per-request fallback.
4. **Do not leave the same invalid identity premise in adjacent checks.** `tests/copy_phase_process.rs:239–242` compares schema/COPY PIDs, and `:261` compares recovery/failed-build schema PIDs. The coordinator confirmed these will use the same validated process-instance identity, with PID retained and validated as a diagnostic. This preserves their separate-process assertions rather than deleting them. This review point is resolved in the agreed proposal, not an outstanding finding.
5. **The correctness safeguards remain independent and must survive unchanged.** Preserve chunk byte limits, thread count, repeated-table and early-index ordering, connector ordering (`:355–416`); exact scans/IDs, PK lookup and actual PK operator, endpoint equality, search, and clean-control equality (`:426–549`); and both managed/direct acknowledgement-failure, no-replay/no-publication, bundle hashes, old/new search, and recovery checks (`:191–262`). Changing only the evidence of process identity does not justify relaxing any of these assertions.

Microsoft documents PID validity only from process creation until termination: [Process Handles and Identifiers](https://learn.microsoft.com/en-us/windows/win32/procthread/process-handles-and-identifiers) (accessed 2026-10-27). This supports rejecting an all-time unique-PID assumption; it does not diagnose the failed run. A cached 256-bit random token is a probabilistic test identity, not a new operating-system identity or production security guarantee. That is proportionate for this bounded fixture.
