## Decisions and overlap to make explicit

1. **Open choices belong in the proposed spec now**, not as already-set issue requirements: S02/S03 distribution policy; S04 home/suffix/script-execution policy; S09 effective lock mode; S10 supported OS floors and source-install recipe. macOS extension `minos 13.3` is current asset evidence, not user approval of a product floor. Windows PE subsystem version does not establish the supported Windows floor. Plain Cargo install lacks the opt-in Windows bundling feature: select/document the intended recipe rather than claiming it was executed and failed.
2. **Avoid duplicate ownership.** S02/S03 own target-specific runtime packaging and dependency checks; S05 owns generic native-probe exit handling; S10 consumes those contracts and owns final cross-platform evidence/document consistency. Source-install policy must agree with S02, not become a second dependency policy. S01/S09 remain narrow storage fixes, not a replacement storage design.
3. **Use only real dependencies.** There is no sequential S01→S02→… chain. Most lanes are independent after the relevant specification decisions and approval; shared files require coordinated ownership, not invented product dependencies. S10 planning can start immediately; its completion waits for all fixes selected for this milestone and fresh evidence. S09 is not the cause of current CI failures or an established support blocker; if included in milestone closure, say that is the selected maintenance scope.
4. **Supplement existing contracts, do not copy them.** Link DC-S2–S5 and the current COPY resource-removal amendment. Preserve rooted confinement, stable/raw Direct identity, owner-bound native lifetime, unknown-containment preservation and approved ceiling removal. S10 records remaining platform evidence against those existing criteria; it must not silently reapprove them, duplicate the whole DC-S5 program, or close aggregate cleanup/release rollout.
5. **Bind approval and evidence honestly.** Give `CBG-PLAT-01` stable requirement/acceptance IDs, exact baseline and canonical Git path; each issue links its applicable IDs and evidence. Keep approval, planned acceptance, actual execution, independent review, platform qualification and deployment separate. Before dependent implementation, freeze the agreed spec and record the real user decision/full Git SHA under the established workflow. The proposed milestone is only grouping in existing Maintenance `P-COD-2`, not a new architecture or authorization.
