# COD-53 installer layout follow-up: app-local runtime versus installed binary path

**Disposition:** read-only, no source, manifests, lockfiles, tests, builds, or Git state changed. This note supplements `full-runtime-proposal.md` and `loader-proposal-delta.md`; it is not an implementation brief or approval. Evidence is from approved S02 at baseline `7038e66ff8271ffddc511f879cf8d28353a09b2d` and pinned dependency/source facts summarized in those reports.

## Finding

With the existing archive installer and command-path contract, the narrowest compatible layout is to keep `codebase-graph.exe` and `k-wiki.exe` exactly in the selected `BinDir` under their existing names, and install the required app-local DLL sidecars in that **same directory**. Do not relocate executables or add launchers. This is the only layout considered here that both (a) lets Windows resolve any direct executable imports before Rust `main` using the executable's application directory and (b) preserves the current direct binary paths. The exact final EXE import set still needs Windows artifact inspection; this layout covers direct DLL imports if present and the complete-extension-preload plan can explicitly load extension dependencies from those files later.

A versioned private payload directory with executables and runtimes together is technically plausible only if the public invocation path is changed to reach those executable paths. The currently shipped installer copies EXEs directly into `BinDir`; README tells archive users to put `codebase-graph` on `PATH`; MCP/hook bootstrap captures the actual `current_exe`, while configured commands use the executable name. A `.cmd` wrapper, launcher, alias, PATH edit, or directory junction would change invocation or install behavior, and this task grants no such design. Keeping EXEs in `BinDir` while placing runtimes in a sibling private directory does **not** satisfy pre-main application-directory resolution for direct imports. The reviewed preload proposal removes any need for process-global DLL search mutation for the known extension closure, but it cannot run before the Windows loader resolves EXE imports.

## Existing public path and ownership evidence

- `release/install/install.ps1` has a `-BinDir` parameter defaulting to `$HOME\.local/bin`; `release/install/install.sh` has `--bin-dir` defaulting to `$HOME/.local/bin`. Both install two named executables directly into that chosen directory. Neither script creates a version-specific program directory, writes a launcher, or edits PATH. Windows docs/README describe using the executable on PATH, not a version-directory command alias.
- The README archive path says to put the downloaded binary on `PATH` and then use `codebase-graph`. MCP config normally records `codebase-graph` as command; daemon/hook creation also captures `std::env::current_exe()` and passes that executable path. Both names and direct process-image identity therefore matter. `k-wiki.exe` is also shipped as a separate executable in the same archive.
- `NativeTarget` archive is currently a flat file set: graph EXE, wiki EXE, checksums, and two installers. It is validated as a closed inventory. A sidecar change must keep this package-inventory authority singular and add sidecars/licenses/manifest to the same deterministic install-root contract, not introduce a second unlinked file list.
- Pinned Ladybug `lbug 0.19.0` calls `LoadLibraryW` on its extension path. The complete-preload proposal may address known extension DLL dependencies without global search-policy mutation, but the application-local directory for initial EXE imports is independently governed by the Windows loader before any Rust initialization.

## Layout options and tradeoffs

| Layout | Preserves existing public binary paths? | Resolves pre-`main` app-local direct DLL imports? | Main consequence |
|---|---|---|---|
| Flat `BinDir`: two EXEs + all required sidecars | Yes | Yes, for imports whose names/versions match the sidecars | Minimal path-compatible choice. DLLs share the selected directory with unrelated user tools, and upgrades update a shared runtime set. Must validate fixed exact sidecar identity; never search arbitrary paths. |
| `BinDir\<version>\` contains EXEs + DLLs; no root binaries | No | Yes | Requires users to invoke versioned path or installer to create path/alias behavior. No such relocation/launcher/PATH behavior is approved. |
| EXEs stay flat, DLLs in private child/sibling folder | Yes | No for direct EXE imports; pre-main code cannot add that folder | Could support later extension-only explicit preload if a reviewed interface allows it, but does not solve initial direct imports. Not a complete bundle layout. |
| Versioned directories plus stable root launchers/`.cmd` shims or symlink/junction | Superficially | Depends on actual process image path and Windows loader semantics | New command kind, process image/path semantics, PATH and upgrade lifecycle. No evidence or approval; do not invent it. |

The flat directory can contain product sidecars next to other programs if a user chooses a shared `BinDir`; Windows resolves dependencies for the process from that application directory, so other binaries there with the same DLL import names can observe these sidecars too. This is a real compatibility consideration, but not a demonstrated conflict. Do not silently alter the install path to avoid it. If the owner rejects sidecars in a shared bin directory, the alternative requires a user-owned decision on dedicated product-directory/command-discovery behavior; no current evidence supports a no-path-change private layout that fixes direct imports.

## Minimal compatible install/preflight sequence (candidate, not settled interface)

1. **Single packaging inventory.** Keep `NativeTarget` as the only authority for Windows sidecar filenames, hashes, sizes, PE machine, dependency closure, licenses, and archive paths. Generate one validated runtime manifest from this inventory. Include the manifest/license/sidecars in package checksums and archive closed-set checks. The runtime must use an embedded trusted manifest or equivalent integrity source, not accept an arbitrary writable installed manifest as authority.
2. **Stage outside the current install.** Extract or copy candidate binaries and all sidecars into an isolated staging directory with the EXEs and their app-local sidecars adjacent. Check exact expected entries, regular-file/no-reparse constraints, hashes, x64 machine, all expected non-system direct/transitive imports and exports, and license provenance. Do not mutate `BinDir` during candidate validation.
3. **Run actual candidate native smoke before replacement.** In a fresh child process launched from this staged directory, use isolated USERPROFILE/cache/database, no extension downloads, and the complete candidate runtime. Exercise actual `Database::new`/reopen (which can replay loaded extensions), JSON and FTS loading/query, and graph reopen/search. `--help`/`--version` alone do not validate extensions. A dedicated S02 probe must check its own process exit immediately; do not count on or repair the general `Assert-Binary` behavior assigned to COD-56. Verify both candidate executables' actual startup imports; run database/extension work through the appropriate supported process path. If an existing installed executable must remain a supported upgrade base, an additional staged compatibility check of that existing executable against the candidate runtime is a possible check, but has not yet been specified or shown necessary; settle it in review rather than silently broadening scope.
4. **Only after all preflight passes, install sidecars into `BinDir` before EXEs.** The DLLs must be present at the unchanged app directory when the new EXE is first launched, so installing binaries first is not safe. Stage sidecars as temporary siblings in `BinDir`, recheck hashes, then place the fixed expected sidecar names. Recheck installed hashes/inventory before replacing either EXE. Only then use the installer's existing per-file temporary-copy/move for both EXEs. Keep public executable names and locations unchanged. If any invalid/missing/incompatible candidate sidecar is found, fail before writing sidecars or replacing either existing executable; this directly gives A04's preflight preservation result without pairwise binary rollback.
5. **Report and bound nontransactional failure.** After successful preflight, a filesystem/lock error or interruption during sequential sidecar installation can leave a partial new sidecar set beside the old EXEs; an error during the existing two EXE moves can leave the existing per-file partial pair risk. The task explicitly excludes an unapproved two-binary rollback redesign and does not promise power-loss atomicity. Do not claim whole-install rollback or “always unchanged on any installation error.” Keep per-file errors clear and do not report successful install until every sidecar and EXE hash is verified. If preserving an existing working installation through mid-sidecar-copy/rename failure is a required contract, a compatible old/new runtime-set strategy or sidecar recovery transaction must be settled and reviewed; the current scope does not specify that guarantee.

## Upgrade/install identity

- A single fixed `BinDir` with root DLL names gives Windows app-local resolution and preserves command paths, but sidecar DLLs become shared entries in that bin directory. The archive's selected runtime identities should be fixed and compatible as a set. On upgrade, sidecar preflight must finish before touching installed sidecars, and the candidate must be proven with its own set. If there is a need to guarantee old binaries work while the DLL set is updated, verify that requirement explicitly; do not infer it from successful candidate smoke. Same-major OpenSSL ABI policy is not enough to demonstrate the transient state with only one of `libcrypto`/`libssl` updated or with interrupted VC runtime replacement.
- A conservative rule that refuses any changed runtime hash at an existing install preserves old sidecars but blocks future runtime security updates. A versioned runtime directory would avoid overwriting old DLLs but cannot satisfy direct EXE imports with binaries kept in current flat paths. Neither is silently chosen here.
- A staged sidecar temp copy plus per-file rename can avoid partial file contents but not make a multiple-DLL set atomic. No code here adds backups, restores, in-use file policy, launcher indirection, or global search behavior.
- Installer scripts currently use arbitrary `BinDir`; placing application-local DLLs there can affect other binaries in that same directory if names collide. That should be covered as a compatibility test/notice under the proposed flat layout or raised as a user-owned install-layout question if the owner deems it unacceptable. It is not authority to rewrite `BinDir` defaults or mutate PATH.

## Required tests and separate Cargo modes

**Archive/installer deterministic tests:** reject missing, duplicate, unknown, malformed, reparse/non-file, wrong-machine, hash-mismatched, wrong-closure and missing-license sidecars; assert `DryRun` and real-install candidate validation occurs before sidecar or EXE destination changes; preserve hashes of both existing EXEs and all existing sidecars on every *preflight* failure; assert errors are clear; prove successful install leaves expected flat names/hashes, and no launcher/PATH/invocation contract changes. Include failures at sidecar staging/individual rename and record honest state; do not add pair rollback unless separately authorized.

**Native Windows tests:** run candidate graph and wiki EXEs with root app-local imports; run real JSON/FTS, reopen/recovery and child/helper process loading under the complete preload proposal; verify correct module origins and pinned lifetimes; test CWD/PATH decoys, foreign already-loaded module, malformed/missing transitive dependencies and incompatible existing runtime. Native Server CI is useful implementation evidence but not A03 desktop qualification.

**A03/A04 acceptance:** exact final archive installed on supported Windows 11 x86_64 desktop, no separately installed OpenSSL/VC runtimes/developer PATH. Record actual OS edition/release/build and artifact hashes. Run graph JSON/FTS/reopen/search plus MCP/k-wiki smoke from the installed flat path. Missing/corrupt/incompatible sidecar cases fail clearly before either existing executable is replaced. No Windows 11 desktop execution is available in this investigation; qualification remains pending.

**Cargo source mode remains separate:** root `default = ["bundled-windows-extensions"]` is the D05d candidate for ordinary `cargo install codebase-graph`; `k-wiki` is unpublished and its existing feature forwarding remains unchanged. A distinct internal `packaged-windows-runtime` feature is only a full-archive build candidate for xtask and must not be in root defaults. It may make archive builds fail closed if packaged runtime metadata/sidecars are absent; it must not make plain Cargo source install claim app-local self-containment. Root default extension bytes and documented native compiler/native-library/runtime-DLL prerequisites are separate from app-local prebuilt layout. Exact A16 Windows source recipe/qualification remains pending.

## Decision / recommendation for coordinator

**Recommended minimal path-compatible proposal:** keep both EXEs directly in the existing `BinDir`; package the fixed, reviewed runtime closure beside them; perform complete candidate archive and actual extension-load preflight wholly in staging; then place and verify sidecars in `BinDir` before replacing either EXE. This preserves existing binary/command paths and needs no launcher or global PATH/DLL-policy changes. It is conditional on final Windows EXE PE evidence, eligible exact sidecar supply, the complete-preload design's independent review, and a clear sidecar-upgrade failure contract.

**Specific unresolved contract question if stronger preservation is required:** On an in-place upgrade where candidate validation passed but copying/renaming a member of the multi-DLL sidecar set fails or is interrupted, must the installer guarantee the old binary+runtime installation remains usable and byte-identical? The existing installer moves the two EXEs individually and the spec explicitly excludes a new pair rollback redesign; it does not currently state DLL-set atomicity. If the answer must be yes, sequential flat sidecar replacement without an additional sidecar recovery contract cannot establish it. A versioned isolated directory would require a changed executable path/launcher or other explicit loader/manifest integration. Do not decide this by implementation convenience. The narrower approved-negative requirement is already clear: missing, corrupt, wrong-architecture or incompatible candidate sidecars must be discovered in staging and must not cause replacement of either existing EXE.

**Avoided:** versioned executable relocation, launcher/shim, persistent PATH edits, `SetDefaultDllDirectories`, arbitrary DLL fallback, Ladybug upgrade, Cargo source-mode rewrite, installer pair rollback, or claim of Windows desktop qualification. None is authorized by this bounded follow-up.
