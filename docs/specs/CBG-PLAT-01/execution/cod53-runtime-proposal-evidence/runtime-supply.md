## Conclusion

There is a technically plausible in-scope OpenSSL provider: build official OpenSSL **3.5.9** for MSVC x64 from the primary OpenSSL release source. The checked-in 0.19.0 Ladybug JSON and FTS PE files import OpenSSL 3 DLL basenames `libssl-3-x64.dll` and `libcrypto-3-x64.dll`; their OpenSSL imports are 3.0 API symbols. OpenSSL documents API/ABI compatibility across releases with the same major version. The exact names follow OpenSSL's Windows/MSVC naming rules (`SHLIB_VERSION=3`, x64 suffix); the final produced DLL exports, dependency closure, and load behavior still require Windows build/test evidence. This source-built candidate is not a third-party binary and does not require changing Ladybug or its extension bytes.

**One real release/redistribution permission gate remains:** Microsoft says VC runtime redistribution is limited to users licensed for Visual Studio and its license terms. This repository's workflow invokes a path under the GitHub-hosted VS 2022 Enterprise installation, but that is not evidence that the repository publisher/maintainer has the required redistribution license. The supplied checkout/configuration contains no evidence settling that right. Do not package VC DLLs until the distribution owner confirms the applicable licensed entitlement (or supplies another legally reviewed route consistent with D01). This is not a finding that Microsoft forbids app-local redistribution: Microsoft lists unmodified runtime files as redistributable subject to valid license/terms. It is a missing permission fact; a build host's possession of files cannot establish it. The user/maintainer owns resolving it.

Other missing items below are implementation design/verification obligations, not grounds to reopen the approved D01/D05 policy. No clean Windows 11 desktop or plain-Cargo native run was performed here.

## Supply candidates and compatibility

### OpenSSL: primary-source build is technically viable, not yet qualified

Candidate source: official release `openssl-3.5.9`, release commit `45e844fa2a14ec92d146bd8f5778ac130b6625fb`, official source archive `https://github.com/openssl/openssl/releases/download/openssl-3.5.9/openssl-3.5.9.tar.gz`; official published archive SHA-256 `603f5602e2eef00d77fbd429d34dcd5822bb301757a1bc9cdb24c670f1eb859a`. OpenSSL source lists 3.5 as LTS through 8 April 2030 as of this investigation; the source release includes `LICENSE.txt` (Apache-2.0). OpenSSL licensing page states 3.0+ uses Apache License 2.0. The Windows/MSVC OpenSSL source derives shared DLL names from the major shared-library version and target suffix. `VERSION.dat` for 3.5.9 has `SHLIB_VERSION=3`; `Configurations/platform/Windows.pm` chooses `.dll`, and `Configurations/platform/Windows/MSVC.pm` adds `-3-x64`. Thus the candidate target output names match the extensions' demanded names exactly: **`libssl-3-x64.dll`, `libcrypto-3-x64.dll`**. Official OpenSSL migration guide says releases with the same major number are API and ABI compatible. On OpenSSL 3.5.9's official `util/libssl.num`/`util/libcrypto.num`, every extension-imported OpenSSL symbol is present and marked introduced in `3_0_0` (including `BIO_new_socket`, which is conditional on `SOCK`). This is strong API/ABI evidence for a 3.x candidate, but actual x64 DLL exports and dependency imports still need automated artifact inspection and Windows load/SQL execution.

This is source, not a prebuilt binary offer; build it in a controlled Windows CI step using the native MSVC x64 OpenSSL target (OpenSSL documents MSVC builds and requires its build tooling). Preserve source archive hash, target/config/compiler, output DLL hashes, export map and recursive PE import report as provenance. Include the Apache license/notice with the DLLs. No ABI/dependency version upgrade is necessary to test this provider: the proposed compatibility claim is same-major runtime substitutability for the already-linked OpenSSL 3 ABI. Still, the exact-version question should be closed by that import/export/load evidence, not this source-level conclusion.

### Existing vcpkg setup is not a DLL provider

Current `.github/actions/setup-native/action.yml` runs unversioned `vcpkg install openssl:x64-windows-static`, copies `libssl.lib`/`libcrypto.lib` to `ssl.lib`/`crypto.lib`, and exports them to MSVC `LIB` for linking. It does not resolve or pin a repository vcpkg baseline/manifest. The explicit **static** triplet is not a source of the dynamic DLLs imported by the extensions; this action does not establish runtime-byte licensing or provenance. Do not reuse it as if it supplied the sidecars. A dedicated official OpenSSL source pin/build is the more auditable compatible route; a future explicitly pinned vcpkg **dynamic** build could also be considered only after proving its exact DLL basenames, exports/closure, source baseline and redistribution terms. No binary from an arbitrary third party is recommended.

### VC runtime: possible app-local bytes, permission is unverified

Direct extension imports are exactly `MSVCP140.dll`, `VCRUNTIME140.dll`, `VCRUNTIME140_1.dll`. The API-set UCRT imports are Windows 10+ system components; Microsoft says UCRT is on Windows 10 and later, which includes the approved Windows 11 desktop. Windows 11 qualification must nevertheless test the actual target build and extension loads. OpenSSL's MSVC-built dynamic DLL may add its own CRT imports; final closure could require the same sidecars or more. Audit actual PE imports recursively for all DLLs (dedupe basenames; separate OS-known/system/API-set contracts from redistributables) before declaring this list complete.

Microsoft's official VS 2022 REDIST page says, **“If you have a validly licensed copy”** of the specified Visual Studio software, listed files can be copied/distributed unmodified subject to terms. It lists unmodified files under `[VisualStudioFolder]\VC\redist` as redistributable, with runtime packages/files subject to license terms; Microsoft’s latest-VC-redist guidance separately says redistribution is permitted only for licensed Visual Studio users. App-local DLL deployment puts runtime DLLs alongside the app; Microsoft calls it a deployment method, though prefers central package deployment for its update servicing. D01's user-approved app-local policy governs here, so central/global installation is not a substitute.

Current repository facts: Windows setup/build workflow explicitly calls `C:\Program Files\Microsoft Visual Studio\2022\Enterprise\VC\Auxiliary\Build\vcvars64.bat`; that identifies a build toolchain path only. It does not prove the project, maintainers, or artifact distributor has the license entitlement to copy and redistribute the VS redist files, nor identify which exact redist versions/bytes are eligible. No Microsoft license record or build-channel grant is in the inspected repo. This is the concrete user-owned legal gate. If entitlement is confirmed, use the eligible official VS redist x64 files **unmodified**, pin their exact source/toolset version and SHA-256, record the applicable license/version provenance, and include them next to both executables. The DLL recursion may show additional eligible VC DLLs; use exact `dumpbin`/`llvm-readobj` imports, not assumed all-files packages. Do not silently replace app-local distribution with “install VC redist separately.”

## Loader/installer constraints and candidate shape (proposal, not approved implementation)

- Locked archive authority `NativeTarget` currently packages only two EXEs, `checksums.txt`, `install.sh`, `install.ps1`; its digest list covers only the two EXEs. Extraction rejects entries outside that exact list. Package inventory and checksums need deterministic entries for each runtime sidecar and license file; preserve NativeTarget as the only authority, not a second package list. The current build has static OpenSSL `.lib` linkage for the executable, but no final PE import evidence here; inspect the actual graph and wiki EXEs as well as extension and OpenSSL DLL imports.
- Installer `Assert-Binary` today verifies each EXE digest and invokes only `codebase-graph.exe --help` / `k-wiki.exe --version`, then after validation copies each EXE. Because D01 requires application-local runtime bytes, the install transaction must place and validate DLL sidecars beside the installed EXEs too; leaving DLLs only in the extracted archive while copying EXEs to another bin directory breaks application-local resolution. These probes cannot prove `LOAD json`/`LOAD fts`. S02 needs a deterministic candidate probe using the *staged archive binaries and staged DLLs*, before either destination EXE is replaced, that starts a fresh isolated extension cache with downloads disabled and actually loads/uses JSON and FTS. Ideally exercise graph creation/reopen and FTS search, or a deliberately narrow native runtime probe command calling the same checked `lbug::Connection` loader path. Validate version/machine/export closure too. Emit explicit native success/failure status; do not treat current setup/version startup as extension validation. This is a narrow S02 safety gate, not the unrelated COD-56 two-file rollback redesign.
- Locked Ladybug 0.19.0 source confirms `ExtensionLibLoader` uses `LoadLibraryW(fullExtensionCachePath)`; no `LOAD_LIBRARY_SEARCH_*` flags. Cache paths resolve under client home `.../.lbdb/extension/0.19.0/win_amd64/...`, so arbitrary DLL search for the *extension path* is not safely constrained by the app executable directory. Microsoft documents that a dependency of a DLL is resolved by module name even when the top-level DLL was loaded by full path. It also checks the loaded-module list by name without regard to origin before normal directory searches. Therefore simply placing app-local OpenSSL DLLs beside an EXE, calling `LoadLibraryW` for them by basename, adding the app directory to global `PATH`, or loading them only by absolute path without checking module identity is not enough.
- A candidate controlled sequence is: before any Ladybug native database/extension load, locate only the approved sibling runtime directory from the running executable; verify every expected sidecar's exact path/hash, machine, required exports and import closure; fail closed if a module of the same basename is already loaded from a different path; explicitly load the exact approved `libcrypto-3-x64.dll` path first, then `libssl-3-x64.dll`, with `LoadLibraryExW(..., LOAD_LIBRARY_SEARCH_DLL_LOAD_DIR | LOAD_LIBRARY_SEARCH_SYSTEM32)` (dependency lookup confined to the package directory and Windows system directory); verify both actual loaded-module paths; retain/pin handles for process lifetime. Loading crypto first avoids resolving `libssl`'s crypto dependency through an already-loaded same-basename module. Ladybug's subsequent `LoadLibraryW` of the cache extension should resolve imports to these already-loaded names. Do not add arbitrary user/cache paths or mutate global PATH. This sequence must be proven against Windows documented loaded-module precedence and exercised in actual process. A selected approved approach should also guard against another thread/dll being loaded first; do not leave a basename race. Do not implement this until parent/reviewer settles the mechanism.
- Initialization cannot be only in CLI `main`: app entrypoints are `src/bin/codebase-graph.rs` and `crates/k-wiki/src/bin/k-wiki.rs`, internal graph workers can be relaunched through `src/bootstrap.rs`/registered worker executable, and callers can enter the public Rust library without either CLI. Native connection entry points include `src/db_writer/access.rs::open_guarded_database`/`connect_ladybug_database` and direct `Connection::new` in `src/api/graph_read.rs`; writes preseed bundled extensions in `src/db_writer/write.rs::prepare_candidate`, and FTS reads preseed in `src/api/graph_read.rs`. Place/route the runtime guard so all these paths, plus a library consumer and helper subprocess, are covered before Ladybug `LOAD`. Keep app-local resolution process-scoped and avoid changing user `PATH`.
- Final security review should test poisoned same-basename DLL earlier on `PATH`, a foreign already-loaded same-name module (must fail clearly, not accept it), missing/corrupt/wrong-architecture DLL, missing export/dependent DLL, and a writable cache extension. These are verification for settled D01 controlled-loading policy, not policy changes. No full security properties were tested here.

## Plain Windows Cargo (A16): minimal default route

Current root Cargo has `bundled-windows-extensions = []` but no root default feature; the Windows asset `include_bytes!` branch in `src/db_writer/extensions.rs` is gated on that feature. `k-wiki` has `default = []` and forwards an opt-in feature. Its Windows release builder explicitly passes the feature; plain root Cargo install does not. Existing `include` globs already carry `assets/ladybug-extensions/0.19.0/**/*.xz` into the crate package.

The smallest Cargo mechanism is set root package `default = ["bundled-windows-extensions"]`; Cargo automatically enables a package's default features unless caller explicitly passes `--no-default-features`. The existing `k-wiki` transitive root dependency enables root defaults unless explicitly disabled, so verify this with exact `cargo install` flows for both delivered binaries and dependency configuration. Keep the same feature gate/name and bytes; no new mechanism, Ladybug change, extension version change, or runtime extension download is needed. `--no-default-features` remains explicit opt-out and is not the approved “plain cargo install” scenario. Verify `.crate` inclusion and installed executable bytes/feature behavior on Windows, plus a temporary empty Ladybug extension cache and disabled extension-download network path. A16's source-native compiler/OpenSSL/VC runtime prerequisites remain documented and distinct from D01 self-contained prebuilt archive. This feature default does not itself supply app-local DLLs or establish Windows runtime prerequisites. The current `.crate` source include already includes compressed assets independent of feature; reviewer supplied prior exact package evidence of 8,451,625 compressed bytes (<10 MiB) for the `--no-verify` package at that snapshot. Recheck final package size in implementation, but default feature does not add archive source files.
