## Bottom line

There is a practical official byte acquisition/provenance path for VC app-local files: obtain a **version-pinned official Visual Studio Community 2022 installation media/component** containing `VC\\Redist\\MSVC\\<toolset-version>\\x64\\Microsoft.VC143.CRT` from a Community-licensed acquisition, then copy only the exact eligible unmodified DLLs listed in VS 2022 REDIST. This is consistent with the selected Community route and Microsoft’s documented source location, but exact files, revision and applicable license still must be captured and validated. The `aka.ms/vc14/vc_redist.x64.exe` public Microsoft redistributable package is also official and content-addressable, but Microsoft documents it as an installer for central installation, not as a documented source for the individual app-local payload; do not unpack/redistribute its internal MSI payload as the DLL source without first establishing that exact method/files are in the applicable REDIST and terms. NuGet packages found during search were unofficial package owners, old, or UWP-specific; no exact Microsoft-maintained NuGet package providing this desktop app-local CRT payload was established.

**Concrete unresolved fact, not an architecture blocker:** no Community 2022 licensed installation/payload source or specific version was acquired/observed in this task, and the GitHub Actions job runs in an Enterprise VS path. The approved license-route decision does not assert the distributor has acquired Community or identify exact eligible installed DLL bytes. For the requested report, user selected that route and asked not to raise another question; report this as a factual provenance prerequisite for release/package supply, not a new policy decision. A reproducible pinned Community install layout/package source plus hashes and its actual applicable terms must enter implementation evidence. If the build pipeline cannot lawfully access the Community-installed REDIST files through that route, S02 cannot ship VC DLLs from the observed GH Enterprise host and must stop pending a different explicitly approved supply route.

The published v3.0.4 Windows EXE import tables prove the already-shipped pair directly imports the same three CRT names as the extensions. These are not merely dependencies of the future OpenSSL DLLs: the initial executable image imports them. Therefore in the existing installed two-EXE layout the initial VC DLLs must be beside **each executable** (or be available through a documented Windows system installation, which approved D01 expressly excludes as the user prerequisite). Loading only the OpenSSL names from some later private directory cannot get through process image initialization if the VC dependencies are missing. This follows from an actual published archive, but v3.0.4 is historical and not the unpublished baseline 4.0.0; inspect final 4.0.0 candidate PE imports before deciding the exact manifest.

## Microsoft primary-source terms and supply options

1. Microsoft's Visual C++ redistributable guidance says distribution of packages, merge modules **and individual binaries** is limited to licensed Visual Studio users and subject to Microsoft Software License Terms. It says the VS 2022 files are in `%VCINSTALLDIR%Redist\\MSVC\\v143` (or `VCToolsRedistDir`), and individual files can be copied directly into an application-local folder, though central package install is recommended for servicing. Source: https://learn.microsoft.com/en-us/cpp/windows/redistributing-visual-cpp-files?view=msvc-170 .
2. The official VS 2022 REDIST page says Community 2022, Professional 2022, and Enterprise 2022 are covered, requires a validly licensed copy and unmodified files, and lists runtime files under `[VisualStudioFolder]\\VC\\redist`; it excludes debug/nonredist and previews. Source: https://learn.microsoft.com/en-us/visualstudio/releases/2022/redistribution . The Community 2022 product terms route was user-selected and linked in the decision record; that is the right license route to evidence, not a generic “the runner had VS installed” inference.
3. Microsoft latest redist URL is version-moving: `https://aka.ms/vc14/vc_redist.x64.exe`. On 2026-10-27 it redirected to `https://download.visualstudio.microsoft.com/download/pr/ebdab8e5-1d7b-4d9f-a11b-cbb1720c3b12/843068991DAAA1F73AD9F6239BCE4D0F6A07A51F18C37EA2A867E9BECA71295C/VC_redist.x64.exe`, HTTP 200; response ETag identifies `843068991DAAA1F73AD9F6239BCE4D0F6A07A51F18C37EA2A867E9BECA71295C`; file SHA-256 `843068991daaa1f73ad9f6239bce4d0f6a07a51f18c37ea2a867e9beca71295c`, 18,731,856 bytes. It is official source/provenance for a version-pinned **central runtime installer**. Primary Microsoft docs at https://learn.microsoft.com/en-us/cpp/windows/latest-supported-vc-redist?view=msvc-170 explain it installs/registers libraries; https://learn.microsoft.com/en-us/cpp/windows/redistributing-visual-cpp-files?view=msvc-170 gives `/layout` to copy package contents and distinct instructions for application-local individual DLLs. Neither says internal MSI/cab payload extracted from the central-installer package itself is the permitted app-local source. I extracted it only under analysis temp for structural inspection and did not install it. Its embedded Burn manifest reports x64 bundle version `14.51.36247.0`, but the CABs contain opaque payload members and this source route does not prove the app-local file REDIST provenance or distribution permission for those exact bytes. **Recommendation:** do not use this package as an implicit bypass around Community/REDIST list/source evidence.
4. NuGet search against NuGet's official search endpoint (`https://azuresearch-usnc.nuget.org/query`) found no Microsoft-owned desktop app-local CRT NuGet for this need. `vc143.wixproj.redist` is third party and wraps the official central installer; `VCLibs.140.Redist.Unpackaged` is third-party-owned UWP runtime; `Microsoft.VCRTForwarders.140` concerns forwarders, not a complete desktop CRT; other CRT packages were third-party/old. Avoid as an arbitrary binary provider or provenance substitute.

### Practical pinned source / workflow recommendation

Use the REDIST directory from a particular licensed VS Community 2022 installation, preferably pin the exact component version/toolset and source package hash in release evidence. On the release build, locate the `Microsoft.VC143.CRT\\x64` app-local files from that explicitly versioned source, copy unmodified DLLs, check each filename against the applicable VS 2022 REDIST list, include required notices, hash/record each output, and fail if an input or expected hash/identity changes. Better: consume versioned Community installation media/cache as an authorized protected release input rather than relying on whichever host VS happens to be installed; if sourcing from Microsoft's layout at job time, pin the Community installer/channel manifest and approved component versions and make the installer identity explicit. The current repository setup action executes under `C:\Program Files\Microsoft Visual Studio\2022\Enterprise\...`; it neither proves a Community licensed build input nor a pinned REDIST source. Do not copy arbitrary Enterprise-host files merely because their DLL names match. Community terms eligibility and exact component files must be recorded by the distribution owner; the previous approved choice settles the route, not those acquisition facts.

- `codebase-graph.exe`: 50,469,888 bytes; SHA-256 `dbc2d8d49b4a6844debafab61623724f69e89e4b6eb0bfd5c6b023a28d03b13f`.
- `k-wiki.exe`: 41,651,200 bytes; SHA-256 `42ea1df2e1048fd3630a8a5b71c84ad58b6aef5313ab49f890cac4c01dac7b1a`.
- Parsed PE32+ x64 imports offline. Both executables directly import **`MSVCP140.dll`, `VCRUNTIME140.dll`, `VCRUNTIME140_1.dll`**, plus Windows DLLs: `bcryptprimitives.dll`, `kernel32.dll`, `api-ms-win-core-synch-l1-2-0.dll`, `advapi32.dll`, `psapi.dll`, `USER32.dll`, `crypt32.dll`, `ws2_32.dll`, `ntdll.dll`; and API-set UCRT names `api-ms-win-crt-{runtime,math,heap,locale,string,convert,time,stdio,environment,filesystem,utility}-l1-1-0.dll`. `k-wiki.exe` and graph exe share the same complete non-system CRT dependency list; the graph exe also directly lists `psapi.dll`.
- These binaries were **not executed**. This import evidence is for v3.0.4 only; cannot silently treat it as exact 4.0.0 or final COD-53 import closure. Coordinator says 4.0.0 release is not yet published; once final candidate exists, parse both exact final PE images and recursively inspect every non-system dependency.

Because both app EXEs import the CRT at process startup, Windows must resolve these names before `main` / Rust bootstrap, so a guard that only runs once Rust starts cannot help if the CRT DLLs are not found. Under D01, put every final PE-required VC sidecar at the application-local executable directory for each app entrypoint; when installer places the two EXEs in the same bin directory, one shared sibling set covers both. For future OpenSSL DLL imports, secure native preloading still must validate/load OpenSSL paths before Ladybug extension `LoadLibraryW`; this report does not alter that loader proposal.

## Exact limits and blocker record

- **What is known:** source may be obtained from eligible unmodified VS 2022 REDIST-listed files. Microsoft's official VC central-installer package is pinned by version, URL, ETag, and hash but is not documented here as a valid app-local DLL payload source. The actual Community REDIST source/version/file hashes have not been acquired or recorded.
- **What is not known / release blocker:** no proof of an acquired/licensed Community 2022 installation available to the actual package publisher, no pinned Community component/REDIST layout, no exact DLL hashes/file-list against REDIST, and no final 4.0.0 EXE imports. Do not claim a fully sourced/legal supply inventory, or ship VC DLLs from GitHub Enterprise runner's unversioned installation, until those facts are recorded. No new user decision asked: Community route is already selected; actual acquisition/publisher compliance is not agent-observable and is a release provenance prerequisite.
- **No behavior qualification:** no Windows build/test/desktop install/load, no execution of v3.0.4, and no A03/A04/A16 qualification asserted. Further investigation intentionally stops at this source/provenance boundary.
