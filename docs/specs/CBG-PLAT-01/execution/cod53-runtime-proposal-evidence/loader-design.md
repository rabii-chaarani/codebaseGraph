- Pinned dependency source was inspected from Cargo.lock-matching `lbug 0.19.0` crate archive. Its Windows extension shim in `lbug-src/src/extension/extension.cpp` implements `dlopen` with plain `LoadLibraryW(fpath.c_str())` (lines 456–460). That is a Windows standard search-policy call, not a strict application-local dependency policy. Extension manager in `extension_manager.cpp` opens the extension path via `ExtensionLibLoader`; its loader object calls `dlopen(path)` and stores the returned module handle. `LoadedExtension` is retained by the database extension manager after successful `init`; the handle lifetime is therefore tied to loaded extension/database manager, not the short preseed call. `unload()` exists but must not be used before callbacks finish. This loader lives **inside the pinned Ladybug dependency**. The Rust project cannot force safe resolution for that `LoadLibraryW` call merely by setting search flags for its own `LoadLibraryExW`; must either (a) establish a narrowly scoped, process-wide safe default *before any Ladybug LOAD* and prove its behavior against Ladybug's exact call, or (b) get a reviewed compatible integration point/upstream change in Ladybug that uses secure `LoadLibraryExW` flags / controlled directories. A Rust helper loading OpenSSL DLLs before extension LOAD is not itself enough to establish safe dependency binding or transitive closure; Windows may unify by module basename with already-loaded DLLs.

## Bounded loader design proposal (subject to reviewer choosing interface)

1. **Choose one app-local layout and one ownership identity.** Sidecars are shipped adjacent to the two official executables in the archive, under one fixed versioned private folder next to the executable (e.g. `runtime/openssl/...`, `runtime/vc/...`) or adjacent root; installer copies them into the same stable installation directory as `codebase-graph.exe` / `k-wiki.exe`. The exact layout should follow sidecar packaging and DLL API constraints. Treat executable/application dir and the sidecar dirs as protected app-owned files, not user cache, CWD, PATH, or `%TEMP%`. Do not add an arbitrary executable-adjacent DLL pick-up from cwd. Avoid versioned sidecar files with no ownership/cleanup story; the installed folder is one identifiable product install and upgrade copies/replaces the expected sidecar names in place only after the existing preflight passes. Do not add rollback of the two EXE copies; specifically do not begin replacing either EXE until sidecar checks and both target-binary checks pass. COD-56's broad generic native nonzero probe fix remains excluded.
2. **Unsettled competing loader hypotheses — not an implementation prescription.** A process-global restricted policy (`SetDefaultDllDirectories`, possibly exact `AddDllDirectory` paths) plus exact-path preload/retained module handles is one hypothesis to test. It mutates the whole process's loader behavior, may affect an embedding application's dependencies/plugins, and cannot simply be undone to restore standard search; public library callers may not consent to that process-wide side effect. The other broad direction is constrain/alter the Ladybug extension load integration point so its DLL load uses explicit safe flags or an application-controlled resolver; that may require an upstream seam or dependency change and is not approved here. Keep both as alternatives for the independent proposal gate. App-local deployment location and import closure can be investigated independently, but neither proves controlled loading. The final graph/wiki executables' direct imports must be inspected because those DLLs resolve before Rust `main`; a Rust bootstrap cannot protect initial executable imports. Pinned Ladybug 0.19.0 calls `LoadLibraryW`, so any proposed mechanism must prove behavior for that exact call, all relevant process/library entrypoints, child workers, already-loaded foreign basename modules and transitive dependencies. Do not set process-global flags, preload modules, add DLL directories, mutate PATH, or modify Ladybug without reviewer-approved proposal and a settled interface. If later reviewing a `LoadLibraryExW` option, Microsoft requires a fully qualified top-level path for `LOAD_LIBRARY_SEARCH_DLL_LOAD_DIR`; directories added via multiple `AddDllDirectory` calls have unspecified search order. These facts constrain review; they do not select a mechanism.
3. **Verification question for the review, not a selected design.** For whichever mechanism is proposed, prove it against Ladybug 0.19.0's `LoadLibraryW` path on the approved Windows 11 baseline, including transitive OpenSSL dependencies, no CWD/PATH lookalikes, and already-loaded foreign basename modules. Windows loaded-module resolution may bind a dependency by basename to a module loaded from an unintended location; tests must establish detection/failure behavior rather than assume absolute paths alone solve this. The direct imports also include VC runtime DLLs and OS API-set/System32 dependencies. Confirm Microsoft's eligible app-local file list and recursive imports for the selected exact bytes; do not indiscriminately ship OS API-set/system DLLs or derive full redistributable closure from direct PE imports alone.
4. **Installer preflight is narrower than changing all probes.** Before creating/installing to destination and before *either* EXE replacement: validate `checksums.txt` inventory against exactly expected binaries+sidecar(s); validate each sidecar's SHA-256 against an expected digest in the trusted artifact inventory (and/or archive-authenticated inventory, with clear provenance); check sidecars are regular non-reparse paths within extracted package and expected PE machine/import set; then execute a dedicated, documented **native-runtime smoke command on each candidate binary**, using candidate-local sidecars and a temporary isolated HOME/cache/database, requiring actual `INSTALL/LOAD json`, `INSTALL/LOAD fts`, small JSON function/query, FTS index create/query, close/reopen where applicable. It must assert nonzero status and useful failure text itself; it must not reuse the generic `Assert-Binary` implementation unchanged because current PowerShell's `ErrorActionPreference=Stop` does not make native exit status a reliable failure and that unrelated defect is COD-56. A special smoke command that tests only imports/`--version` is insufficient. Ensure temporary files/child process are cleaned even on exceptions; do not put fixture payload under installation destination. Then perform the current per-file binary moves. This is not a two-binary transaction redesign and does not promise rollback if second move fails. Missing, hash-mismatched, malformed, architecture-incompatible, or load-failing sidecars stop before both destination binaries are touched. Test on existing destination files by byte-hash equality before/after each failure.
5. **Archive, installed-loader, and provenance evidence must agree.** CI/archive unit tests should reject missing, duplicate, unexpected, nonregular/reparse, tampered, wrong-arch, and hash-mismatched sidecars. Package hashes/checksum records include all runtime sidecars; archive SHA/provenance already covers final compressed archive, but sidecar-specific hashes are necessary to audit contents and installed files. `NativeTarget` remains one packaging authority. For installed-file verification, check only expected files and verify path/hash before process launch; smoke both binaries in a clean child process with empty PATH except OS-safe paths, temporary cwd, clean user extension cache, and no development-installed OpenSSL/VC. Capture Windows OS/edition/build, toolchain, extension/runtime PE imports and all hashes. Build-host smoke or Server CI remains CI evidence only; without a Windows 11 desktop, A03/A04 qualification remains **pending**, not inferred.

## Sidecar installation/upgrade details and negative cases in scope

- Existing `install.ps1` resolves an archive extraction dir, checks each executable hash and probes CLI, then creates BinDir and moves EXEs individually. Native artifact `dry_run_installer` invokes only packaged script dry-run. For COD-53: expand packaged/installer hash validation for the expected runtime set; test both installers' dry-run against a valid package; ensure required sidecar present/inventory-valid and candidate runtime smoke succeeds *before* destination mutation; preserve existing destination EXEs and sidecars byte-for-byte on every preflight failure. For real install, create `BinDir` only after preflight, copy/install sidecars at fixed paths and move both binaries in existing order. The current installer has no unrelated-data deletion. Upgrades need same stable sidecar identity/path so existing DB/cache state and binaries unaffected; old orphaned runtime files may be left in the install dir unless cleanup policy is separately agreed. Do not claim pairwise atomicity or roll back one EXE when second replacement fails.
- Corrupt/incompatible bundled-runtime negatives: sidecar absent; altered digest; malformed/wrong machine PE; missing required OpenSSL or VC dependency; OpenSSL DLL has a same-name malicious CWD/PATH decoy; transitive DLL absent; extension incompatible by native loader/init; runtime smoke false/nonzero. For all *preflight-detectable* negatives, assert no destination executable or runtime file changed. A test for replacement failure after the mutation phase is not an invitation to design pair rollback under this slice.
- Race/ownership: packaged extracted files are not a trust boundary by filename alone; rely on expected inventory+hash and archive hash/provenance from approved release, reject symlinks/reparse paths. Installation directory protections are OS/installer configuration (current scripts install to user path under `$HOME\.local\bin` by default). If app-local DLLs are user-writable alongside exe, the adversary model includes user who can replace their own installation; do not claim protection against that principal. However do not load from an unrelated writable search directory. If a shared system install is later chosen, directory ACL and updater behavior need separate requirements.
