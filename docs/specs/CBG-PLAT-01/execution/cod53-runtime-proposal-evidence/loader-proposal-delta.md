## Why the narrow route can work

Microsoft documents that DLL dependencies are resolved by module name even when the parent uses a full path, and that already-loaded modules are considered before ordinary directory search. It also documents that `LoadLibraryExW` with `DLL_LOAD_DIR | SYSTEM32` restricts directory lookup for the preload's dependencies; PIN keeps accepted modules loaded until process termination. Consequently, **all** non-system dependency names already resident from verified intended paths can satisfy Ladybug's later plain `LoadLibraryW` imports without changing the process default search policy. The report's warning that preloading *OpenSSL alone* is insufficient is sound; the stronger proposal preloads/verifies the entire closure, including VC and any additional discovered non-system modules. These are materially different proposals.

Do not describe this as making all later `LoadLibraryW` calls safe. The argument is limited to the known verified extension/runtime import closure. It does not police arbitrary embedding-host/plugin loads or defend against a principal already executing hostile code in-process.

## Required details in the settled implementation brief

1. **Closed set before code execution.** Derive normal/delay-import closure and required exports from exact final EXEs, extensions and sidecars. Validate all expected bytes/paths/machines first; preload dependency-first, so a parent's initialization cannot consume an unverified non-system dependency. Keep runtime files in one trusted application-owned directory where practical. Explicitly inspect runtime-loaded optional modules/provider/helper paths; a static import-table closure does not prove such loads absent. This is an evidence task, not evidence that an extra module exists.
2. **Existing modules and retention.** Inspect all relevant existing same-basename modules, not merely trust the first lookup result; fail clearly on an unacceptable origin before loading Ladybug/extensions. Validate returned module path/identity after exact-path loads, and pin/retain the complete accepted set process-wide. Do not accept a different-path module just because its exports appear compatible; no PATH/CWD fallback. One-time internal initialization must precede the project's native use in every process, including helper children. No speculative hostile concurrent injection is an additional gate here.
3. **Earlier than database open.** There is a concrete ordering trap: actual `src/db_writer/access.rs:142` calls `Database::new`; pinned Ladybug `src/main/database.cpp:140` invokes recovery, and `storage/wal/records/load_extension_record_replay.cpp:9–12` can replay `loadExtension`. Therefore placing initialization only in `preseed_ladybug_extensions` or immediately before explicit `LOAD fts` is insufficient for reopen/recovery. Initialize/verify before `Database::new` on all supported library/product paths, not only CLI main. Preserve library consumers' process search defaults.
4. **Validate extension input too.** Actual pinned `extension_manager.cpp:13–35` loads an optional extension-loader file from the cache if present before the main extension. Existing seeding skips preexisting files. The settled package path must establish which exact extension/helper files Ladybug can load and check their expected identity (or clearly reject unsupported cache state) before native open/LOAD. Preloading runtime DLLs alone cannot authenticate a cache extension or an optional cache loader. This is a concrete reachable integrity path, not a request for a global loader policy or cache redesign. Preserve approved cache behavior except integrity required by R02; surface a real contract conflict if found.
5. **Process baseline and source mode.** Inspect final executable imports: Windows maps direct imports before Rust starts. A private runtime subdirectory does not by itself satisfy those imports. If final EXEs import a required sidecar, packaging must place it where initial app-local loading finds the intended bytes; do not infer this from static OpenSSL link setup. An embedding host may already own VC/OpenSSL modules. The loader must fail clearly on an incompatible packaged baseline rather than silently rebind it. Do not impose packaged-directory identity on A16's separately documented source prerequisite mode or claim universal embedding compatibility. No evidence currently demonstrates an unavoidable conflict requiring an owner decision; exact artifact/baseline tests determine whether one exists.
