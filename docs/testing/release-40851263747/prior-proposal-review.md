The proposed real-Bash fixture directly closes that test gap (proposal lines17,45-55).
2. **The smallest proposed correction matches GitHub's documented immutability lifecycle.** GitHub explicitly recommends draft → attach assets → publish, and states assets and tags lock after publication. Proposal lines34-37 delay publication until local-versus-remote archive AND sidecar bytes match. This is stronger than trusting names or uploaded checksum text alone. [GitHub immutable releases, “Best practices for publishing immutable releases”](https://docs.github.com/en/code-security/supply-chain-security/understanding-your-software-supply-chain/immutable-releases), accessed 2026-10-29.

Official release-list documentation states only users with push access receive draft listings. REST asset download supports octet-stream responses, including redirect or direct streaming. These APIs can support the bounded algorithm; no hosted digest metadata or added dependency is needed. [Release API](https://docs.github.com/en/rest/releases/releases?apiVersion=2022-11-28); [asset API](https://docs.github.com/en/rest/releases/assets?apiVersion=2022-11-28), accessed 2026-10-29.
4. **Latest-version protection occurs at the irreversible boundary.** Recomputing semantic-version latest selection immediately before publication protects a delayed draft from using creation-time state (proposal line37; regression line52). GitHub documents that drafts cannot be latest, and newly published releases otherwise default to latest. Existing non-cancelling release serialization remains intact; the proposal does not claim protection from arbitrary out-of-band owner actions. [Release API, `make_latest`](https://docs.github.com/en/rest/releases/releases?apiVersion=2022-11-28).

## Finding

### IRP-01 — Make ambiguous-response recovery observable in the planned fixture
- **Category:** Improvement; not an established defect or decision-critical gap.
- **Priority:** Improvement, non-blocking for implementation.
- **Location:** Proposal line37 (“No implicit write retry on ambiguous responses”) and regression lines47-54 (normal publication replay but no explicit accepted-write/lost-response scenario).
- **Mechanism:** A mock that only returns successful write responses can pass while an accidental immediate retry remains untested. The important recovery claim is that a server-accepted draft POST or publish PATCH whose response is lost causes this attempt to stop; a later resume discovers and verifies the resulting draft/published state without creating a duplicate or writing a frozen release.
- **Counterevidence:** The algorithm already forbids implicit retries and specifies state reconciliation; the post-publication replay test already covers much of the final immutable state. Thus this is a test-strengthening recommendation, not a missing behavior decision.
- **Remedy / resolution evidence:** Production should include closed-fixture cases that persist a successful create/publish mutation but return nonzero once; assert no same-attempt second mutation, then resume and assert exact-tag draft reuse or immutable verification-only success. This fits existing tests/file ownership and does not require live release evidence, new public behavior or a new delivery gate.
